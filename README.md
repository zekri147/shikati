# شيكاتي

تطبيق ويب صغير لإيلوناك لمتابعة شيكات العملاء من زوهو بوكس، ثم تسجيل إيداعها في بنك AGB (في المرحلة الثانية).

الحالة الحالية: **المرحلة الثالثة — التثبيت على الهاتف وصفحة الشرح.** تسجيل الإيداع يعمل منذ المرحلة الثانية، وطلبات الكتابة إلى زوهو موجودة فقط في `src/modules/deposit.ts`.

من يستطيع تسجيل الإيداع يحدده المتغير `DEPOSIT_ROLES` في `wrangler.toml`: القيمة `admin,rep` تعني المدير وكل المندوبين، والقيمة `admin` تعطّل الإيداع لغير المدير.

عنوان التطبيق المنشور:

```
https://shikati.zekri3047.workers.dev
```

## البنية

| الجزء | الأداة |
|---|---|
| الخادم والواجهة | خادم كلاود فلير (Cloudflare Workers) يقدّم الملفات الثابتة من مجلد `public` |
| التخزين | قاعدة كلاود فلير (D1): المستخدمون، الجلسات، محاولات الدخول، سجل العمليات، تخزين مؤقت |
| زوهو | رمز تجديد من تطبيق (Self Client)، يجدّده وسيط صغير في غوغل لأن كلاود فلير لا يصل إلى خادم الرموز الأمريكي لزوهو (راجع `RELAY.md`) |

```
src/index.ts            توجيه الطلبات وحماية الصفحات
src/auth.ts             الدخول، الجلسات، الأدوار، حد المحاولات
src/admin.ts            إدارة المستخدمين وسجل العمليات
src/zoho.ts             رمز الوصول وطلبات القراءة من زوهو
src/modules/cheques.ts  منطق أقسام الشيكات
src/modules/index.ts    قائمة الوحدات: تُضاف هنا الأقسام الجديدة لاحقاً
web/                    الواجهة: React وTailwind ومكونات Radix (عربية، من اليمين لليسار، الوضع الداكن افتراضي)
web/public/             الملفات الثابتة: الخطوط والشعارات والأيقونات وعامل الخدمة وسياسة الأمان
dist/                   ناتج البناء (npm run build)، لا يُحفظ في المستودع
migrations/             جداول قاعدة البيانات
scripts/create-user.mjs إنشاء أول حساب مدير
```

## لماذا D1 وليس KV

القفل ضد الضغط المزدوج في المرحلة الثانية يحتاج إدخالاً ذرّياً يرفض الطلب الثاني فوراً، و(KV) يتأخر توزيع تحديثاته بين الخوادم. كما أن سجل العمليات وعدّ محاولات الدخول يحتاجان قراءة دقيقة وبحثاً بالتاريخ والمستخدم.

## أسبوع التشغيل المتوازي

في صفحة الإدارة قسم «مطابقة الأسبوع» يقرأ من زوهو فقط، ويعرض لآخر 7 أيام:

- **إيداعات التطبيق:** هل لكل منها إيداع مرتبط في زوهو، وحالة «مودع في البنك» أو «محصّل»؟
- **إيداعات من خارج التطبيق:** شيكات AGB المودعة أو المحصّلة دون أن يسجّلها التطبيق، أي من القسم القديم أو يدوياً. التاريخ هنا آخر تعديل للدفعة، وهو تقريبي.

## التثبيت على الهاتف

- ملف التثبيت `web/public/manifest.webmanifest`، والأيقونات في `web/public/icons/` مولّدة من رمز إيلوناك الأصلي.
- عامل الخدمة `web/public/sw.js` يحفظ الملفات الثابتة فقط، ولا يحفظ أي طلب إلى `/api`.
- آخر بيانات وصلت من الخادم (الشيكات والتحصيل والمستخدم) تُحفظ في ذاكرة المتصفح على الهاتف (`web/src/lib/cache.ts`) لتُعرض فوراً عند الفتح، ثم تُحدَّث. المفتاح يحمل اسم المستخدم، وما هو أقدم من يومين لا يُعرض، وتُمسح كلها عند الخروج والدخول. الإيداع لا يُفتح قبل وصول البيانات الجديدة.
- عند تغيير الملفات الثابتة، غيّر قيمة `VERSION` في `sw.js` حتى تُحذف النسخة القديمة من الهواتف.
- صفحة الشرح على العنوان `/help`، ورابطها في صفحة الدخول وفي الشريط العلوي.

## تسجيل الإيداع

بعد ضغط «أودعت» وتأكيد البطاقة، يفعل الخادم ما يلي بالترتيب، بنفس طريقة دالة `deposer_agb` في زوهو:

1. يتحقق أن دور المستخدم مسموح له بالإيداع.
2. يقفل الشيك بإدخال سطر في جدول `deposits` مفتاحه معرّف الدفعة، فلا يبدأ إيداعان لنفس الشيك معاً.
3. يقرأ الدفعة من زوهو، ويرفض إن كان لها إيداع سابق، أو كانت حالتها غير «في الحوزة»، أو لم تكن في «Cheques in Hand» نحو ELONAC، أو تغيّر مبلغها أو رقمها عمّا ظهر في البطاقة.
4. ينشئ الإيداع في بنك AGB مرتبطاً بالدفعة.
5. يتحقق من الربط، وإن لم يجده يحذف الإيداع.
6. يحدّث الحالة إلى «مودع في البنك»، ويضيف سطراً في سجل الدفعة باسم الموظف.
7. يحفظ النتيجة في جدول الإيداعات وفي سجل العمليات.

| حالة القفل | المعنى |
|---|---|
| تم | الإيداع مسجّل، ولا يمكن تكراره من التطبيق |
| لم يتم | فشل قبل إنشاء أي إيداع، أو أُلغي الإيداع، فيمكن المحاولة مجدداً |
| بانتظار التحقق | انقطع الرد بعد محاولة الإيداع. لا إعادة تلقائية: يتحقق المدير في زوهو ثم يحرّر الشيك من صفحة الإدارة |

## قواعد التصنيف

- **تنتظر الإيداع (الرقم الرئيسي):** مجموع الأقسام الثلاثة «في الحوزة» أدناه.
- **في الحوزة:** الحالة «في الحوزة» والحساب «Cheques in Hand»، ثم تُقسم حسب الوجهة: ELONAC، أو ROSTOMIA، أو فارغة.
- الشيكات «في الحوزة» المسجّلة في حساب آخر (مثل Endorsed Cheques) أو وجهتها «Autre Fournisseur» لا تدخل في أي قسم.
- **آخر 5 إيداعات:** القائمة لا تحتوي تاريخ الإيداع، فالترتيب بآخر تعديل للدفعة.
- قائمة الشيكات تُخزَّن دقيقة واحدة، وزر «تحديث» يجلبها من زوهو مباشرة.

## الأمان

- الرموز السرية مشفّرة بخوارزمية (PBKDF2-SHA256) بـ 100000 تكرار وملح لكل مستخدم.
- الجلسة في ملف تعريف (cookie) من نوع HttpOnly وSecure وSameSite=Strict، تنتهي بعد 12 ساعة (المتغير `SESSION_HOURS`).
- قاعدة البيانات تخزّن بصمة رمز الجلسة فقط، لا الرمز نفسه.
- بعد 5 محاولات فاشلة لنفس الاسم خلال 15 دقيقة يُقفل الدخول 15 دقيقة، وبعد 20 محاولة من نفس العنوان كذلك.
- إيقاف المستخدم يحذف جلساته فوراً.
- كل طلب كتابة يُرفض إن لم يأتِ من نفس الموقع، وسياسة أمان المحتوى (CSP) تمنع أي شيفرة خارجية.
- رسائل الخطأ المعروضة عامة، والتفاصيل تُكتب في سجل الخادم فقط.

## التشغيل لأول مرة

الطريق الأسهل من لوحة كلاود فلير دون أي أداة على جهازك: راجع ملف `DEPLOY.md`.

أو من سطر الأوامر:

```bash
npm install
npx wrangler login
npx wrangler d1 create shikati
```

انسخ قيمة `database_id` التي يطبعها الأمر الأخير إلى ملف `wrangler.toml`، ثم:

```bash
npm run db:migrate:remote
npx wrangler secret put ZOHO_RELAY_URL
npx wrangler secret put ZOHO_RELAY_KEY
npm run deploy
node scripts/create-user.mjs --remote
```

بدل الأمر الأخير يمكنك وضع السر `SETUP_TOKEN` وإنشاء أول مدير من صفحة `/setup`، وهي تعمل مرة واحدة فقط.

بعدها افتح العنوان الذي يطبعه أمر النشر، وادخل بحساب المدير، وأنشئ حساب أمين من صفحة الإدارة.

## رمز تجديد زوهو

يحصل عليه الوسيط في غوغل بنفسه بالدالة `exchangeCode`، ويحفظه في خصائصه. الخطوات في الملف `RELAY.md`.

## التجربة المحلية

انسخ `.dev.vars.example` إلى `.dev.vars` واملأ القيم، ثم:

```bash
npm run db:migrate:local
node scripts/create-user.mjs --local
npm run dev
```

## إضافة قسم جديد لاحقاً

أنشئ ملف وحدة في `src/modules/` يطبّق الواجهة `AppModule`، وأضفه إلى `src/modules/index.ts`، ثم أنشئ مكوّن العرض في `web/src/features/` وأضفه إلى `MODULES` في `web/src/pages/app.tsx` بنفس المعرّف.
